### 文档目的

本文档用于与导师确认项目价值、业务范围、核心能力和验收方向。本文档只描述“系统需要解决什么问题、达到什么效果”，不提前限定具体的数据结构、技术框架和工程实现；相关内容将在需求范围确认后进入设计阶段。

## 1. 项目概述

### 1.1 背景

投研工作通常会跨越多次独立会话：

- 研究员第一次形成对公司或行业的判断；
- 后续继续跟踪验证条件、风险和催化剂；
- 新信息出现后修正甚至推翻原判断；
- 在下一次财报、调研或复盘时继续处理未解决的问题。

普通 Agent 主要依赖当前会话。新会话开始后，研究员往往需要重新介绍自己的覆盖范围、研究逻辑和跟踪事项。

直接保存全部历史聊天也不能解决问题，因为其中包含大量临时要求、重复信息、过时判断和敏感内容，还可能把不同研究员的观点混在一起。

### 1.2 项目定位

本项目拟设计一套可扩展的主动跨会话记忆逻辑：

> 系统主动发现可能值得长期保留的信息，判断是否应该保存，记录来源和有效状态，处理重复与替代，并在未来真正相关的任务中主动恢复。

通用逻辑之上可以定义不同投研场景。本期选择“个股投资假设持续跟踪”作为完整验证场景，并用“调研问题持续跟踪”作为轻量扩展示例，用于初步验证同一套核心逻辑的场景扩展能力。

项目不试图在 20 天内覆盖所有投研业务，而是回答两个问题：

1. 主动记忆能否改善投研任务的跨会话连续性？
2. 同一套记忆逻辑是否具备扩展到不同投研场景的潜力？

### 1.3 “主动”的含义

- 一次会话或阶段性任务完成后，系统主动识别候选记忆，不要求用户每次都说“请记住”。
- 新任务开始前，系统主动寻找相关记忆，不要求用户手动翻历史记录。
- 新信息与旧记忆矛盾时，系统主动识别重复、冲突和替代关系。
- 系统主动提出记忆更新建议，但不能擅自替研究员改变投资判断。

### 1.4 核心原则与术语

#### 核心原则

- 记忆首先服务于研究员自己的连续工作流，不代表经过验证的客观投资事实。
- 用户明确表达的观点和修改优先于系统推断；系统推断不能自动成为用户的正式判断。
- 写入时以准确为先，使用时以相关、当前有效和可追溯为前提。
- 用户应始终知道系统记住了什么、为什么记住、何时使用，并能够进行干预。
- 本期验证的是原型能力和场景扩展潜力，不声称达到生产级投研、合规或数据安全标准。

#### 术语说明

| 术语 | 含义 |
| --- | --- |
| 候选记忆 | 从会话中发现、但尚未完成保存决策的信息 |
| 待确认记忆 | 系统认为可能值得保存，但需要用户确认后才能作为当前记忆使用的信息 |
| 活动记忆 | 已保存、当前有效、可以在相关任务中使用的信息 |
| 历史记忆 | 已被替代、过期或撤销，仅用于回顾和追溯的信息 |
| 未解决研究问题 | 投研业务中仍需继续调查的问题，不等同于“待确认记忆” |
| 抽取置信度 | 系统对自己是否正确理解用户表达的把握，不表示投资判断正确的概率 |

## 2. 投研记忆场景

投研业务中的记忆需求不止投资假设，还包括：

| 场景 | 需要长期保留的内容 | 跨会话价值 |
| --- | --- | --- |
| 个股投资假设跟踪 | 核心假设、验证条件、风险、催化剂 | 判断原投资逻辑是否仍然成立 |
| 调研问题跟踪 | 未解决问题、管理层反馈、下次追问事项 | 避免每次调研重新梳理 |
| 行业持续跟踪 | 重点指标、观察周期、核心变量 | 延续行业研究框架 |
| 研究项目管理 | 当前进度、待办、关键决策 | 恢复中断的研究任务 |
| 研究偏好 | 常用比较口径、关注指标、输出偏好 | 减少重复说明 |
| 投资复盘 | 原判断、实际结果、偏差原因 | 支持经验积累和复盘 |

其中，“个股投资假设跟踪”最适合作为首个场景，因为它同时包含：

- 长期有效的信息；
- 明确的公司和研究员归属；
- 判断状态的持续变化；
- 新旧观点冲突和替代；
- 来源、时间和版本要求；
- 多用户对同一家公司持有不同观点的可能。

## 3. 通用记忆需求

### 3.1 记忆生命周期

```text
用户会话
  → 发现候选记忆
  → 保存 / 待确认 / 丢弃 / 敏感拦截
  → 活动记忆
  → 被强化 / 被修正 / 被替代 / 过期 / 撤销
  → 在相关新任务中被主动使用或作为历史记录被回顾
```

需要区分三类不同含义的状态：

- 候选处理状态：决定一段信息是否进入长期记忆；
- 记忆有效状态：决定一条已保存记忆现在能否被主动使用；
- 业务进展状态：描述某项投资假设、验证条件或研究问题本身的进展。

例如，“这条内容需要用户确认后才能保存”和“这个调研问题还没有得到答案”属于不同概念，不应混为同一种状态。具体状态模型在设计阶段确定。

### 3.2 什么值得记忆

系统优先保留三类信息：

| 类别 | 判断标准 | 投研示例 |
| --- | --- | --- |
| 偏好 | 会持续影响未来分析方式 | “分析医疗器械时优先看现金流” |
| 稳定事实 | 描述用户相对稳定的工作上下文 | “研究员 A 主要覆盖医疗器械” |
| 长期事项 | 会在未来会话中继续验证、更新或完成 | 投资假设、风险、验证条件、调研问题 |

系统通常不应保留：

- “这次回答短一点”等当前任务临时指令；
- 闲聊和没有未来用途的内容；
- 一次性的短期市场波动；
- 模型缺少证据的猜测；
- 密码、账户、真实持仓、交易指令等禁止信息。

### 3.3 每条记忆需要说明什么

每条记忆都应能够回答以下问题：

| 问题 | 要求 |
| --- | --- |
| 这是谁的记忆？ | 明确所属研究员，保证多用户隔离 |
| 属于什么场景？ | 如投资假设、调研跟踪、研究偏好 |
| 关于什么对象？ | 公司、行业、研究主题或用户自身 |
| 具体记住什么？ | 一条清晰、原子化的内容 |
| 内容是什么性质？ | 区分用户观点、用户提供的事实、外部事实和系统推断，避免将观点表述为客观事实 |
| 为什么记住？ | 说明未来用途或保存理由 |
| 来自哪里？ | 可以回溯到一个或多个来源会话及对应的用户表达 |
| 什么时候形成？ | 记录观察和确认时间；相对时间表达应保留原始语境，避免跨会话后失去含义 |
| 现在是否有效？ | 区分当前活动、待确认、被替代、过期和撤销等情况；删除作为单独的用户控制需求处理 |
| 业务进展如何？ | 在适用场景中说明假设是否被支持、问题是否解决等，且与记忆是否有效相互区分 |
| 系统理解得有多确定？ | 表示抽取置信度，而不是投资判断正确概率 |
| 是否敏感？ | 标记敏感级别并执行相应限制 |
| 与其他记忆是什么关系？ | 支持父子关联、重复强化和新旧版本 |

### 3.4 观点、事实与推断的边界

- 研究员表达的投资假设、风险判断和关注重点，应明确归属于该研究员，不能被描述成已经验证的公司事实。
- 会话中引用的数据或外部事实，应保留其来源语境；本期系统不负责独立验证事实真实性。
- 系统可以识别潜在变化或提出更新建议，但基于模型推断形成的新投资判断必须经过用户确认。
- 当系统无法判断某段内容是用户正式观点、临时讨论还是系统推断时，应保守处理，不直接作为活动记忆使用。

### 3.5 通用能力与场景规则的边界

通用记忆逻辑负责：

- 多用户隔离；
- 候选发现和价值判断；
- 来源、时间、有效性和敏感性；
- 重复、冲突、替代和版本管理；
- 相关记忆检索；
- 人工确认、修正、撤销和删除；
- 使用记录和审计。

每个投研场景单独定义：

- 场景中有哪些具体记忆类型；
- 不同记忆之间如何关联；
- 什么情况属于冲突或状态变化；
- 什么任务需要优先召回哪些记忆；
- 场景的业务验收标准。

这样既不会把系统写死在“投资假设”上，也不需要在 20 天内为所有投研场景分别开发一套系统。

## 4. 通用功能需求

### FR-01 多用户隔离

- 每个会话和每条记忆必须属于明确的用户。
- 用户 A 的私有记忆不能出现在用户 B 的检索结果、回答上下文或管理页面中。
- 隔离必须由系统规则保证，不能只依赖模型自行判断。
- 本期可以使用虚拟用户验证隔离逻辑，但应明确这不等同于已经完成真实身份认证和生产级权限体系。
- 隔离验收应覆盖记忆保存、检索、使用、查看、修改和历史回顾等完整流程。

### FR-02 候选记忆发现

- 系统在一次会话或阶段性任务完成后，主动寻找偏好、稳定事实和长期事项。
- 候选内容必须原子化，一条记录只表达一个判断或事项。
- 系统必须识别候选所属场景、研究对象和来源。
- 用户明确表达优先于模型推断。
- 候选发现的具体触发方式在设计阶段确定，但应保证相关记忆能够在后续新会话使用前完成处理。

### FR-03 记忆价值判断

系统将候选分为：

| 决策 | 适用情况 | 后续行为 |
| --- | --- | --- |
| 自动保存 | 用户表达明确、未来用途清晰、风险可接受 | 成为活动记忆 |
| 待确认 | 表达含糊、属于弱推断或可能与旧记忆冲突 | 用户确认前不主动使用 |
| 丢弃 | 临时指令、闲聊、短期事实或没有未来用途 | 不进入长期记忆 |
| 敏感拦截 | 命中禁止保存的信息 | 不保存原文 |

本项目以写入准确性优先：宁可少记，也不应让错误记忆长期影响后续研究任务。

敏感拦截在本期主要指“禁止信息不进入长期记忆”。如果信息在进入记忆流程前已经由外部模型处理，则该能力不等同于模型调用前的数据防泄漏；本项目通过只使用虚构或公开脱敏案例控制该风险。

### FR-04 来源与有效性

- 每条活动记忆必须至少具有一个可回溯来源。
- 同一内容被多次表达时，应增加来源证据，而不是生成大量重复记忆。
- 有明确期限的事项到期后不再作为当前有效内容。
- “下一季度”“三季报”等相对时间或事件时间需要保留形成时的语境，跨会话恢复时不能产生时间歧义。
- 用户可以撤销、修正或删除自己的记忆。
- 撤销、历史保留和删除代表不同的用户意图；具体保留边界需要在设计前根据演示和审计需求进一步确认。
- 历史版本可以用于回顾，但不能被当作当前判断自动使用。

### FR-05 重复、冲突和替代

系统需要区分：

| 关系 | 示例 | 处理 |
| --- | --- | --- |
| 重复 | 多次强调“重点看现金流” | 保留一条记忆，增加证据 |
| 补充 | “也需要关注应收账款” | 与原记忆并存 |
| 状态变化 | 某假设得到部分支持 | 保留判断并更新状态 |
| 明确替代 | “不再看装机，改看耗材复购” | 新判断生效，旧判断进入历史版本 |
| 模糊冲突 | 新表达与旧内容矛盾但不明确 | 待用户确认 |

用户手动修正和明确的新陈述优先级最高。模型根据新信息自行推断的投资判断变化，只能作为待确认建议。

记忆是否当前有效与其业务进展需要分别表达。例如，一个投资假设可以仍是当前关注对象，但证据状态已经“被削弱”；一个研究问题可以作为有效记忆保留，但业务状态仍是“未解决”。

### FR-06 相关记忆使用

- 新任务开始时，系统根据当前用户、场景、研究对象和任务意图寻找记忆。
- 只使用当前有效且与任务相关的少量记忆。
- 当前用户的新指令优先于历史偏好。
- 被替代、过期、撤销和待确认的内容不得作为当前记忆使用。
- 用户观点只能作为该用户的研究上下文使用，不得改写为未经验证的客观结论。
- 页面应展示“本轮使用了哪些记忆”和来源。

### FR-07 用户管理

用户可以：

- 查看系统记住了什么；
- 查看记忆来源、时间和状态；
- 确认待处理记忆；
- 修正、撤销或删除记忆；
- 查看某条记忆的历史版本；
- 查看某次回答使用了哪些记忆。

### FR-08 可解释性与用户控制

- 系统应向用户说明一条信息为什么被保存、为什么在当前任务中被使用。
- 用户应能够区分系统自动保存的内容、等待确认的内容和系统提出的更新建议。
- 当记忆关系、有效性或用户意图不明确时，系统应优先请求确认或不使用，而不是自行扩大解释。
- 用户关闭或修正一条记忆后，后续任务不得继续把旧内容作为当前有效判断使用。

## 5. 场景一：个股投资假设持续跟踪

### 5.1 场景目标

帮助研究员跨多次会话维护：

- 当前投资假设；
- 验证条件；
- 风险和催化剂；
- 尚未解决的跟踪问题；
- 投资逻辑的历史变化。

### 5.2 示例

以下公司和数据均为虚构。

#### 会话一：形成初始判断

研究员 A：

> 我主要覆盖医疗器械。对星海医疗，我现在的核心判断是手术机器人装机增长会带动业绩。下一季度装机量同比超过 20% 才算验证。主要风险是医院资本开支放缓，先跟踪到三季报。

系统应记住：

- 覆盖事实：研究员 A 主要覆盖医疗器械；
- 投资假设：手术机器人装机增长将带动业绩；
- 验证条件：下一季度装机量同比增长超过 20%；
- 风险：医院资本开支放缓；
- 跟踪期限：三季报。

#### 会话二：判断发生变化

研究员 A：

> 最新数据里装机量只增长了 8%。我现在觉得装机不是主要逻辑，后续改为观察耗材复购收入，三季报重点看耗材收入占比能不能超过 30%。医院资本开支放缓的风险仍然需要关注。

系统应：

1. 找到原来的装机增长假设；
2. 记录装机数据未达到原验证条件，并将原假设作为已被替代的历史判断保留；
3. 保存新的耗材复购假设；
4. 将新的验证条件关联到新假设；
5. 继续保留用户明确表示仍然有效的风险；
6. 保留两次判断的来源和时间。

#### 会话三：恢复上下文

研究员 A 新开会话：

> 继续看星海医疗，三季报最需要关注什么？

系统应主动恢复：

- 当前有效假设：耗材复购成为主要增长逻辑；
- 当前验证条件：耗材收入占比是否超过 30%；
- 用户明确保留的风险：医院资本开支放缓。

系统不应把旧的装机量验证条件当作当前判断。

### 5.3 场景验收

- 能正确形成假设、验证条件、风险和期限；
- 验证条件能够关联到对应假设；
- 明确的新判断能够替代旧判断；
- 新会话只恢复当前有效的研究逻辑；
- 可以展示假设演进及来源；
- 另一研究员研究同一家公司时，不使用研究员 A 的私有观点。

## 6. 场景二：调研问题与后续事项跟踪

### 6.1 场景目标

初步验证同一套核心记忆逻辑能否扩展到另一类投研任务：记录调研后仍未解决的问题，并在下一次调研前主动恢复。

### 6.2 示例

研究员 B 在一次虚构调研后表示：

> 远峰材料的客户库存已经开始下降，但还不能确认是否回到正常水平。下次沟通要继续确认库存周期，以及四季度是否存在进一步降价压力。

系统应记住：

- 未解决研究问题一：客户库存是否已经恢复正常；
- 未解决研究问题二：四季度是否存在进一步降价压力；
- 使用场景：下一次公司沟通或调研准备。

后续会话中，研究员 B 表示：

> 最新反馈确认客户库存已经恢复正常，但降价问题仍然没有明确答案。

系统应：

1. 将库存问题标记为已解决并保留来源；
2. 继续保留降价压力问题；
3. 当用户询问“下次调研还需要问什么”时，只主动返回尚未解决的问题。

### 6.3 扩展验证要求

该场景不单独建设完整界面和评测体系，只需验证：

- 可以复用候选发现、来源、状态、版本和检索逻辑；
- 不需要重新定义候选发现、来源、有效性和使用等核心能力；
- 能通过少量端到端案例正确恢复未解决问题。

该结果只能说明框架具备初步的场景扩展能力，不能据此直接得出“已经适用于所有投研记忆场景”的结论。

## 7. MVP 范围

### 7.1 本期必须完成

- 至少 3 个虚拟研究员的记忆隔离；
- 通用记忆生命周期；
- 会话或阶段性任务完成后的主动候选发现；
- 保存、待确认、丢弃和敏感拦截；
- 来源、时间、有效性、敏感级别和版本；
- 区分研究员观点、事实语境和系统推断；
- 重复、冲突和替代处理；
- 新任务中的主动相关记忆使用；
- 用户查看、确认、撤销和删除；
- 完整实现投资假设场景；
- 用少量案例验证调研问题场景；
- 离线评测、基线对比和轻量演示页面。

### 7.2 本期不做

- 不自动读取公告、财报、研报和实时行情；
- 不接入真实投研数据和内部办公系统；
- 不实现多人共享记忆和审批；
- 不从点击、停留时间等行为中学习隐式偏好；
- 不做自动提醒、邮件通知和任务调度；
- 不建设复杂知识图谱或多 Agent 系统；
- 不执行或推荐真实交易。

## 8. 评测与验收指标

### 8.1 评测数据

计划构造：

- 3 个虚拟研究员；
- 3 家虚构公司；
- 约 30 个跨会话脚本；
- 至少 80 条候选记忆；
- 至少 24 组重复、补充、状态变化或替代样例，各主要关系类型均应有覆盖；
- 至少 30 个后续任务。

上述数量是本期拟定规模，最终应结合 D1～D2 形成的黄金案例和标注工作量确认。评测集应同时包含正常案例、容易混淆的边界案例和跨用户负向案例；用于需求讨论和规则调整的案例，应与最终报告中的核心测试案例适当区分，避免只验证已经反复调试过的样例。

### 8.2 对比方案

| 方案 | 说明 |
| --- | --- |
| 无记忆 | 新会话不提供历史信息 |
| 朴素记忆 | 直接保存会话摘要并按相似度选取 |
| 主动记忆 | 进行价值筛选、状态管理、冲突替代和相关性判断 |

### 8.3 核心指标

以下为 MVP 拟定目标，需在黄金案例和标注规则确认后冻结：

| 指标 | MVP 拟定目标 |
| --- | --- |
| 记忆写入精确率 Precision | ≥ 85% |
| 应保存记忆的召回率 Recall | ≥ 75% |
| 场景记忆类型识别 Macro-F1 | ≥ 80% |
| 重复、补充、状态更新和替代判断准确率 | ≥ 85% |
| 相关记忆 Recall@5 | ≥ 85% |
| 无关注入率 | ≤ 10% |
| 已失效或被替代记忆错误使用次数 | 0 |
| 跨用户私有记忆泄漏次数 | 0 |
| 活动记忆来源完整率 | 100% |
| 主动记忆相比无记忆的跨会话任务正确率提升 | ≥ 15 个百分点 |
| 主动记忆相比朴素记忆的跨会话任务正确率提升 | 拟定 ≥ 10 个百分点 |

主要指标口径：

- 记忆写入精确率：被系统保存的记忆中，人工标注认为应该保存的比例；
- 应保存记忆的召回率：人工标注应该保存的内容中，被系统正确保存的比例；
- Recall@5：每个后续任务所需的黄金记忆中，出现在前 5 条候选结果中的比例；
- 无关注入率：实际提供给回答环节的记忆中，与当前任务无关的比例；
- 任务正确率：回答是否正确恢复了当前有效研究上下文，并避免使用错误用户、过期或被替代内容。

黄金标签、原子记忆匹配规则、关系类型定义和任务评分标准应在正式运行实验前冻结。跨用户泄漏和失效记忆错误使用的“0 次”只表示在本期测试集上必须零失败，不代表已经达到生产级安全水平。

最终报告至少人工复核 20 个任务。自动评分只能辅助，不能完全替代人工判断；涉及观点归属、版本替代和无关注入的案例应优先人工复核。

### 8.4 小规模业务验证

优先邀请 1～2 位具有投研经验的用户使用虚构案例完成任务并访谈：

- 抽取出的内容是否符合日常研究表达；
- 哪些内容不值得记忆；
- 研究时间线是否有助于快速恢复上下文；
- 来源、版本和待确认机制是否可信；
- 最希望增加哪个投研场景。

如果无法安排完整试用，至少应邀请导师或一位熟悉投研流程的人员评审核心记忆类型、10 个黄金案例和失败案例。该验证用于判断方向和业务表达是否合理，不作为正式用户研究结论。

## 10. 20 天可行性判断

当前范围以“可运行、可评测、可演示的研究原型”为标准，在以下前提下有望于 20 个工作日内完成：

- 通用逻辑只实现本期明确需要的能力，不建设大型平台；
- 投资假设场景完整实现，第二场景只做扩展性验证；
- 使用虚构数据，不等待内部数据和系统权限；
- 演示界面保持轻量；
- D2 冻结记忆判断标准和黄金案例；
- D13 后原则上不增加核心功能。

本期不以生产级身份认证、高并发、正式合规审计和真实数据安全上线为完成标准。上述能力如果成为验收要求，需要重新评估周期和范围。

如果进度落后，依次删减：

1. 复杂可视化，只保留对话、记忆卡片和时间线；
2. 第二场景的界面展示，只保留自动化案例；
3. 记忆编辑，只保留确认和撤销。

不能删减多用户隔离、来源追溯、版本替代、主动使用和评测，否则课题核心不成立。

## 11. 最终呈现方案

### 11.1 现场演示

建议使用 5～7 分钟：

1. 用研究员 A 的三次会话展示投资假设形成、变化和恢复；
2. 展示哪些内容被保存、待确认或丢弃；
3. 展示当前记忆及历史版本；
4. 切换用户，证明相同公司不会发生观点串用；
5. 用研究员 B 的调研案例展示核心逻辑具有扩展到第二场景的潜力；
6. 展示无记忆、朴素记忆和主动记忆的指标对比；
7. 展示两个失败案例及项目边界。

### 11.2 最终交付物

- 可运行原型和启动说明；
- 需求文档和场景说明；
- 合成评测集与标注规则；
- 对比实验报告；

## 12. 合理性与业务边界

从需求定义看，当前方案能够覆盖“个人研究员跨会话持续跟踪研究状态”的核心场景：

- 能恢复原来的研究逻辑和未解决事项；
- 能处理判断变化和历史版本；
- 能保留来源和时间；
- 能允许不同研究员持有不同观点；
- 能减少反复介绍背景的成本。

但本项目还不能称为完整投研助手，因为本期不解决：

- 最新事实和市场数据获取；
- 原始材料真实性和数据质量；
- 团队协作、审批和正式合规留痕；
- 真实投资建议或交易执行。

因此，汇报时应将项目表述为：

> 一个面向投研连续工作流的主动记忆能力原型，而不是完整的智能投研平台。

## 13. 待导师确认

1. “通用记忆能力 + 投资假设主场景 + 调研问题扩展示例”的定位是否合适？
2. 投资假设、验证条件、风险和调研问题是否符合真实研究流程？
3. 演示是否可以全部使用虚构公司和合成数据？
4. 最终验收更看重通用能力、业务场景还是实验指标？
5. 是否有一位研究员可以帮助快速评审黄金案例？
6. 研究偏好和覆盖事实是否需要纳入本期完整评测，还是仅作为扩展示例？
7. 当前拟定的评测规模和指标门槛是否适合作为 20 天原型目标？
8. 本期将敏感能力限定为“禁止信息不进入长期记忆”，该边界是否可以接受？
9. 对撤销、历史保留和用户删除的需求，导师更看重用户控制还是完整审计回顾？

## 14. 一句话总结

> 本项目希望让投研 Agent 主动记住真正具有长期价值的研究上下文，在多用户隔离前提下处理记忆的形成、变化和失效，并通过投资假设与调研跟踪两个场景验证其业务价值和初步扩展能力。
