## Context

本设计将项目视为绿地项目，不以当前验证性代码的入口、模块和存储为约束。目标是在 20 个工作日内形成一个可信、可演示、可评测的通用主动记忆原型，而不是一次性建设生产级记忆平台。

### 本次设计审查结论

需求文档和 OpenSpec 规范已经明确区分“通用记忆能力”和“具体场景规则”，总体架构方向正确。

```text
阶段一～三：完成通用记忆核心
    → 阶段四：增加投资假设场景
    → 阶段五：增加调研问题场景并完成评测
```

### “通用优先”不等于脱离实例

如果完全不使用实例，通用接口很容易成为无法验证的抽象；如果一开始只使用投资实例，核心又容易被投资概念污染。

因此本设计采用三类示例：

1. 阶段一至三使用测试专用的 `TestScenarioPolicy` 和中性工作场景，只验证通用机制；
2. 阶段四使用“星海医疗”实现第一个正式业务场景；
3. 阶段五使用“远峰材料调研问题”实现第二个正式业务场景，证明扩展时不需要修改核心生命周期。

`TestScenarioPolicy` 只存在于测试和演示夹具中，不作为正式业务场景发布。

### 总体结构

```text
                              ┌─────────────────────┐
用户对话 ────────────────────>│    Agent Runtime    │
                              └──────────┬──────────┘
                                         │
                              查询记忆 / 提交对话
                                         │
                                         ▼
┌──────────────────────────────────────────────────────────────┐
│                    通用 Memory Core                          │
│ Capture │ Admission │ Lifecycle │ Recall │ Governance        │
│ 用户隔离、来源、状态、版本、审计和删除规则不可被场景放宽     │
└───────────────────────┬───────────────────────┬──────────────┘
                        │ 调用场景契约           │ 持久化
                        ▼                        ▼
             ┌────────────────────┐    ┌──────────────────┐
             │ ScenarioPolicy     │    │ SQLite 单文件数据库│
             ├────────────────────┤    │ Python 精确向量计算│
             │ Test（仅测试）     │    └──────────────────┘
             │ InvestmentHypothesis│
             │ ResearchQuestion   │
             └────────────────────┘
```

依赖方向必须保持为：

```text
Memory Core 定义 ScenarioPolicy 接口
具体场景实现 ScenarioPolicy
应用组装层注册具体场景
Memory Core 不导入任何具体场景模块

domain / ports 不依赖 Config、Observability、Agent 或第三方基础设施
application / adapters 可以依赖共享 Observability
各可执行入口按需读取自己的 Settings，不要求无关模型凭据
顶层 agent_lab 包不主动导入任何功能模块
```

第一版作为模块化单体运行，不拆微服务，不引入消息队列。模型负责理解自然语言，普通程序负责身份、权限、状态和最终写入。

### 通用核心与场景插件的职责边界

| 通用 Memory Core 负责 | ScenarioPolicy 负责 |
| --- | --- |
| 可信用户上下文和所有权隔离 | 场景标识和可用记忆类型 |
| 候选的四种准入结果 | 类型说明和场景抽取提示 |
| 来源、观察时间和内容性质 | 允许的业务关系 |
| active、superseded、expired、revoked | 业务进展值及其转换规则 |
| revision、历史和事务一致性 | 哪些业务表达构成明确冲突或替代 |
| duplicate、supplement、replace、conflict 的通用动作语义 | 不同任务下的类型优先级 |
| 召回上限、有效性过滤和空结果 | 场景相关性特征和排序权重 |
| 确认、修正、撤销、删除和审计 | 场景自己的验收样例 |
| 敏感持久化边界 | 不得放宽任何核心安全与治理规则 |

## Goals / Non-Goals

**Goals:**

- 阶段一至三先完成不依赖投资语义的通用记忆闭环。
- 从阶段一开始定义并验证 `ScenarioPolicy` 扩展边界。
- 从阶段一开始保证所有记忆属于明确用户，不能只依赖 Prompt 隔离。
- 完成候选发现、准入、版本、召回、管理、删除和审计。
- 让投资假设和调研问题以插件形式复用同一套核心逻辑。
- 每个阶段结束时都有可以运行、演示和停止的结果。
- 先验证正确性，再根据实际延迟和数据规模增加异步、混合检索等优化。

**Non-Goals:**

- 不兼容当前原型代码结构。
- 不在需求仍待导师确认时冻结复杂场景 DSL。
- 不让通用核心理解“投资假设”“验证条件”或“调研问题”等业务词义。
- 不在证明需要之前实现 Kafka、Redis、微服务、HNSW 调优和复杂任务调度。
- 不接入真实投研数据、正式身份认证、交易和合规审批。
- 不验证用户提供的事实是否真实。
- 不通过一个配置文件解决所有未来场景。

## 示例

### 通用核心示例：项目协作记忆

阶段一至三使用下面的中性示例。测试策略临时提供 `preference`、`ongoing_item` 和 `stable_context` 三种类型，但核心只把它们当作场景返回的合法标识。

#### 会话一：形成通用记忆

用户：

> 以后项目周报默认用表格。接口重构下周还要继续跟进。这次回答短一点。

期望结果：

| 原子内容 | 类型 | 准入结果 | 原因 |
| --- | --- | --- | --- |
| 项目周报默认使用表格 | preference | 自动保存 | 明确、持续有效的偏好 |
| 接口重构下周继续跟进 | ongoing_item | 自动保存 | 跨会话仍需推进 |
| 这次回答短一点 | 无 | 丢弃 | 只约束当前任务 |

#### 会话二：明确替代

用户：

> 周报以后不用表格了，默认给我简短要点；接口重构仍然下周继续。

期望变化：

```text
旧偏好“周报默认使用表格”
    → superseded

新偏好“周报默认使用简短要点”
    → active

“接口重构下周继续”
    → 仍为一个 active 记忆，仅增加新的来源证据
```

#### 会话三：新会话恢复

用户：

> 帮我整理一下接下来的项目事项。

系统可以召回“接口重构下周继续”；如果生成周报，可以使用“默认简短要点”。系统不得继续使用已经被替代的“默认用表格”。

这个示例只验证通用能力：

- 原子候选；
- 自动保存和丢弃；
- 重复强化；
- 明确替代；
- 当前与历史；
- 主动召回；
- 当前指令优先；
- 来源和用户控制。

### 第一个正式场景：星海医疗投资假设

阶段四再实现以下业务语义：

#### 会话一

研究员 A：

> 对星海医疗，我现在的核心判断是手术机器人装机增长会带动业绩。下一季度装机量同比超过 20% 才算验证。主要风险是医院资本开支放缓，先跟踪到三季报。

投资场景插件将其解释为：

| 类型 | 内容 |
| --- | --- |
| hypothesis | 手术机器人装机增长将带动业绩 |
| validation_condition | 下一季度装机量同比增长超过 20% |
| risk | 医院资本开支放缓 |
| time_horizon | 跟踪到三季报 |

#### 会话二

研究员 A：

> 装机量只增长了 8%。我现在觉得装机不是主要逻辑，后续改为观察耗材复购收入，三季报重点看耗材收入占比能不能超过 30%。

期望由投资场景规则识别为“明确替代”，再由核心完成 revision、状态和来源的一致性更新。

#### 会话三

研究员 A：

> 继续看星海医疗，三季报最需要关注什么？

系统只应返回当前的耗材复购假设、30% 验证条件和仍有效的风险，不得把旧装机条件作为当前判断。

### 第二个正式场景：远峰材料调研问题

阶段五实现：

> 远峰材料的客户库存还不能确认是否恢复正常，下次继续确认库存周期。

形成 `open_question`，业务进展为 `unresolved`。用户后来明确“库存已经恢复正常”后，业务进展变为 `resolved`。

这里用于验证：

- `resolved` 是场景业务进展，不等于核心的 `superseded` 或 `revoked`；
- 调研准备时优先召回未解决问题；
- 增加该插件不需要修改核心状态、版本、隔离和治理规则。

## Decisions

### 阶段一：通用契约、可信记忆卡片和用户隔离

**建议周期：D1～D4**

#### 阶段目标

先不调用模型，也不实现任何正式业务场景。通过手动命令和测试证明：

- 一条通用记忆如何表达；
- 记忆属于谁；
- 来源、内容性质和有效状态如何保存；
- 用户 A 无法查看或修改用户 B 的记忆；
- 核心如何通过 `ScenarioPolicy` 接受场景差异；
- 核心代码不依赖投资或调研模块。

#### 本阶段建设内容

1. 建立 Memory Core 的模块边界：

```text
domain       通用实体、值对象和状态
application  通用用例
ports        Repository、Model、Embedding、ScenarioPolicy 接口
adapters     SQLite 等基础设施实现
composition  注册场景并组装应用
```

2. 定义最小 `ScenarioPolicy` 契约：

```text
scenario_id
memory_types
business_progress_values
allowed_relations
capture_guidance
relation_rules
recall_priorities
```

第一阶段只确定职责和类型边界，不设计可视化配置平台，也不承诺接口以后绝不调整。

3. 建立通用数据结构：

| 字段 | 含义 |
| --- | --- |
| memory_id | 跨版本稳定的逻辑记忆标识 |
| owner_id | 可信上下文指定的所属用户 |
| scenario | 注册的场景标识 |
| subject | 记忆对象 |
| memory_type | 由场景声明的类型标识 |
| content | 一条原子内容 |
| assertion_kind | 用户观点、用户提供事实、外部事实或系统推断 |
| lifecycle_status | active、superseded、expired 或 revoked |
| business_progress | 可选的场景业务进展 |
| source_turn_id | 来源 turn |
| observed_at | 观察时间 |

4. 使用 Python 标准库 `sqlite3` 保存 `MemoryItem`、初始 `MemoryRevision` 和
   `Evidence`。默认数据库位于 `.agent-lab/memory.db`，测试使用临时数据库，
   不要求安装或启动独立数据库服务。

5. 所有公开操作显式携带可信 `PrincipalContext`。Repository 不提供不带 owner 范围的普通业务方法。

6. 使用测试专用 `TestScenarioPolicy` 和“项目协作记忆”夹具进行手动创建、查询和历史过滤。

#### 本阶段流程

```text
应用组装层注册 TestScenarioPolicy
    → 测试或管理命令携带 PrincipalContext
    → Core 校验场景和类型
    → 创建记忆卡片
    → SQLite 事务保存
    → 当前用户可查看
    → 其他用户不可探测
```

#### 阶段验收

- 可以手动创建、查看和列出通用记忆；
- 每条记忆都有明确用户、来源、类型、内容性质和状态；
- 未注册场景和非法类型会安全失败；
- 跨用户读写和猜测 identifier 的负向测试全部通过；
- 非活动记忆不会出现在当前记忆列表；
- Core 的依赖检查中不存在 `investment`、`research_question` 等正式场景模块；
- 所有测试不调用外部模型。

#### 本阶段不做

- 不自动从聊天中抽取；
- 不判断重复和替代；
- 不做向量检索；
- 不接 Agent；
- 不实现投资假设和调研问题；
- 不做异步任务。

### 阶段二：通用捕获、准入和待确认流程

**建议周期：D5～D8**

#### 阶段目标

让 Core 能够在不知道具体业务含义的前提下，通过当前场景策略处理一轮会话，并为每个候选给出且只给出一种结果：

```text
自动保存 / 待确认 / 丢弃 / 敏感拦截
```

这一阶段解决“如何发现候选、如何安全决定是否进入记忆”，暂不解决复杂的新旧关系和语义召回。

#### 本阶段建设内容

1. 定义 `TurnEnvelope`、`Candidate`、`AdmissionDecision`、`ReviewItem` 和 `CaptureResult`。

2. Core 向已注册的 `ScenarioPolicy` 获取合法类型和抽取提示，而不是在 Prompt 或校验代码中写死投资类型。

3. 在模型调用和持久化前执行敏感预检，禁止密码、账户秘密、真实持仓和交易指令进入长期记忆正文或向量。

4. 使用结构化模型输出原子候选。模型可以建议类型、对象、内容性质、时间、理由和置信度，但不能决定 owner、来源和观察时间。

5. 通过通用确定性规则处理准入：

| 情况 | 决策 |
| --- | --- |
| 明确表达、具有持续价值、类型合法、风险低 | 自动保存 |
| 弱推断、表达含糊或可能冲突 | 待确认 |
| 临时要求、闲聊或一次性信息 | 丢弃 |
| 禁止持久化的信息 | 敏感拦截 |

6. 第一版同步处理并保证 source turn 幂等。重试不能制造重复候选、ReviewItem、Evidence 或活动记忆。

7. 提供最小确认和拒绝操作，使 pending 内容在确认前始终与 active 记忆隔离。

#### 本阶段流程

```text
TurnEnvelope
    → 可信身份和已注册场景校验
    → 敏感预检
    → ScenarioPolicy 提供抽取约束
    → 模型输出原子候选
    → 通用结构校验
    → 通用准入规则
    → 自动保存 / 待确认 / 丢弃 / 拦截
    → 返回 CaptureResult
```

#### 示例

使用“项目协作记忆”会话一：

| 内容 | 决策 |
| --- | --- |
| 周报默认用表格 | 自动保存 |
| 接口重构下周继续 | 自动保存 |
| 这次回答短一点 | 丢弃 |
| 弱推断出的偏好 | 待确认 |
| 账户密码 | 敏感拦截且不保留原文 |

#### 阶段验收

- 一轮对话可形成多个原子候选；
- 候选类型必须来自当前注册策略；
- 临时要求不会进入长期记忆；
- 弱推断只进入待确认，确认前不可召回；
- 敏感内容不会出现在候选正文、记忆、日志、向量和测试快照中；
- 同一个 turn 重复处理结果幂等；
- 更换测试策略后，Core 无需修改即可接受另一组合法类型。

#### 本阶段不做

- 不自动替代旧记忆；
- 不做复杂关系分类；
- 不做语义召回；
- 不实现正式投研类型；
- 不做异步 worker 和一致性 token。

### 阶段三：完成通用生命周期、主动召回和用户治理

**建议周期：D9～D13**

#### 阶段目标

完成不依赖正式业务场景的通用闭环：

```text
形成记忆
    → 重复、补充、修正、替代或冲突
    → 保存当前版本和历史
    → 新会话只召回当前且相关的内容
    → 用户能够确认、修正、撤销和删除
```

阶段三通过后，可以把 Memory Core 视为独立完成；后续阶段只增加场景插件和验证，不再补核心主流程。

#### 本阶段建设内容

1. 完善通用记录：

- `MemoryItem`：跨版本稳定的逻辑身份；
- `MemoryRevision`：某个时间点的不可变内容；
- `Evidence`：来源会话和允许保存的表达；
- `Relation`：duplicate、supplement、corrects、replaces、conflicts 等通用关系；
- `Usage`：提供给回答和实际使用的版本；
- `AuditEvent`：不包含禁止正文的关键动作；
- `SuppressionMarker`：防止删除内容被旧来源自动重建。

2. 严格区分：

```text
候选准入：auto_save / pending / discard / blocked
记忆有效性：active / superseded / expired / revoked
业务进展：由 ScenarioPolicy 定义
```

3. Core 负责关系动作的一致性，场景策略只判断哪些类型允许建立关系、哪些表达在该场景属于明确替代。

4. 同用户、同场景、同对象和兼容类型先在 SQLite 中做结构化匹配。Embedding
   作为普通记录保存在 SQLite 中，再由 Python 对严格限定 owner 范围后的
   小规模候选执行精确相似度计算；本原型不依赖数据库向量扩展。

5. 关系处理：

| 关系 | Core 的通用动作 |
| --- | --- |
| duplicate | 保留一个逻辑记忆，增加来源 |
| supplement | 两条原子记忆并存，保存关系 |
| correction | 创建新 revision，旧 revision 留在历史 |
| replacement | 新记忆 active，旧记忆 superseded |
| ambiguous conflict | 创建待确认项，不改变当前记忆 |

6. 提供 `query_memory`，强制按以下顺序执行：

```text
可信 owner 范围
    → 已注册场景
    → 排除 pending、superseded、expired、revoked、deleted
    → 对象和类型过滤
    → 语义相关性和场景优先级
    → 最低阈值
    → 最大条数和 token 预算
```

7. 提供当前列表、待确认、详情、来源、历史、使用记录、确认、拒绝、修正、撤销和删除。

8. 删除清除 content-bearing revision、来源片段和向量，只保留不可恢复正文的最小审计和抑制标记。

9. SQLite 不提供 Row-Level Security。所有 Repository 查询必须把
   `owner_id` 写入 SQL 条件，所有用户数据表保留 owner 与复合外键约束，
   并通过直接调用 Repository、猜测 identifier 和跨用户写入测试验证存储
   边界。生产化时再评估迁移 PostgreSQL 与增加 RLS。

10. Agent Runtime 通过框架无关适配器在回答前查询、回答后提交会话并报告使用情况。

#### 示例

使用通用示例的三次会话验证：

```text
会话一：保存“周报默认用表格”和“接口重构下周继续”
会话二：明确用“默认简短要点”替代旧周报偏好，并重复接口事项
会话三：只召回当前偏好和仍需推进的事项
```

同时验证：

- 用户 B 即使知道 memory id 也无法查看、关联、召回或删除用户 A 的内容；
- 用户撤销新偏好后，该偏好立即停止自动召回；
- 用户删除接口事项后，旧 turn 重处理不会自动恢复正文；
- 没有足够相关记忆时返回空集合，不为填满 Top-K 注入无关内容。

#### 阶段验收

- 重复表达只强化来源，不制造副本；
- 明确替代后只有新内容是 active；
- 模糊冲突不会擅自改变当前记忆；
- 旧版本可以回顾，但不会进入正常回答上下文；
- 用户可以确认、拒绝、修正、撤销和删除；
- 三个虚拟用户的读、写、匹配、召回、历史、管理和使用记录均通过隔离测试；
- 当前任务指令优先于历史偏好；
- 删除后内容不能从 Memory Core 的旧来源自动重建；
- Core 的完整端到端测试只依赖 `TestScenarioPolicy`，不依赖正式投研插件。

#### 本阶段不做

- 不实现投资假设和调研问题；
- 不做复杂全文与向量融合；
- 不做 HNSW 调优；
- 不做后台摄取任务；
- 不建设正式身份认证或完整管理平台。

---

### 阶段四：投资假设场景插件

**建议周期：D14～D16**

#### 阶段目标

在已经完成的通用 Core 上实现第一个正式场景，回答两个问题：

1. 投资假设需要哪些类型、业务进展、关系和召回优先级？
2. 完整三轮投研案例是否只通过注册插件就能运行？

#### 本阶段建设内容

1. 实现 `InvestmentHypothesisPolicy`，声明：

- hypothesis；
- validation_condition；
- risk；
- catalyst；
- time_horizon。

2. 定义场景业务进展，例如 forming、supported、weakened、rejected。它们不得改变核心 active、superseded、expired 和 revoked 的含义。

3. 定义场景关系：

- 验证条件属于哪个假设；
- 风险或催化剂与哪个假设相关；
- 哪些用户表达构成明确假设替代；
- 哪些新数据只能削弱假设而不能替用户改变观点。

4. 定义投研任务下的召回优先级。例如财报准备优先当前假设、验证条件和风险。

5. 使用“星海医疗”三次会话执行捕获、演进、召回和来源展示。

6. 增加 Core 依赖守卫：投资插件可以依赖 Core，Core 不得反向导入投资插件或出现投资类型常量。

#### 场景验收

- 会话一形成原子假设、验证条件、风险和期限；
- 会话二明确替代旧假设，同时保留仍有效风险；
- 会话三只召回耗材复购假设、30% 验证条件和当前风险；
- 模型根据新数据推断观点变化时只能产生待确认项；
- 研究员 A 和 B 对同一公司的不同观点完全隔离；
- 除修复通用缺陷外，实现投资插件不需要修改 Core 生命周期和状态定义。

#### 本阶段不做

- 不实现调研问题；
- 不接真实投研数据；
- 不验证外部事实；
- 不实现团队共享和审批；
- 不把投资类型升级为核心内置类型。

### 阶段五：调研问题场景、扩展性验证和交付评测

**建议周期：D17～D20**

#### 阶段目标

用第二个正式场景证明扩展边界成立，并用同一测试集比较主动记忆、无记忆和朴素摘要。

#### 本阶段建设内容

1. 实现 `ResearchQuestionPolicy`：

- open_question；
- follow_up；
- finding；
- unresolved / resolved 业务进展；
- 调研准备时优先未解决问题。

2. 使用“远峰材料库存周期”完成问题形成、后续跟进和明确解决。

3. 执行扩展性检查：

```text
新增场景允许变化：
场景包、注册配置、场景测试和场景评测样例

新增场景不应变化：
Core 状态、版本、所有权、删除、审计和通用关系动作
```

4. 构造相互分离的开发集和最终测试集，比较：

```text
无记忆
朴素会话摘要
主动结构化记忆
```

5. 计算：

- 写入 Precision 和 Recall；
- 类型 Macro-F1；
- 重复、补充和替代判断准确率；
- Recall@5；
- 无关注入率；
- 失效记忆误用；
- 跨用户泄漏；
- 跨会话任务正确率。

6. 根据实际失败案例决定是否增加异步捕获、全文与向量融合、HNSW 或更强 usage citation。没有证据的优化不阻塞原型交付。

#### 示例：最终评测任务

输入：

> 研究员 A 新开会话：继续看星海医疗，三季报最需要关注什么？

| 检查项 | 正确结果 |
| --- | --- |
| 当前假设 | 耗材复购 |
| 当前验证条件 | 耗材收入占比超过 30% |
| 当前风险 | 医院资本开支放缓 |
| 旧装机条件 | 不得作为当前判断使用 |
| 用户 B 的观点 | 不得出现 |
| 来源 | 能回溯会话二 |

第二个任务：

> 下次去远峰材料调研，还有什么没有确认？

只应返回当前用户尚未解决的调研问题；已经 resolved 的库存问题不得继续作为未解决事项返回。

#### 阶段验收

- 调研问题插件复用同一 Capture、Lifecycle、Recall 和 Governance；
- 第二场景没有引入新的核心生命周期状态；
- 开发案例和最终测试案例相互分离；
- 三种方案完成同集对比；
- 跨用户泄漏和失效记忆误用为零；
- 活动记忆来源完整；
- 至少人工复核 20 个任务；
- 输出指标、失败案例、已知边界和工程增强决策；
- 完成演示脚本、文档和录屏兜底。

#### 本阶段不做

- 不为了“架构完整”实现没有评测证据的优化；
- 不把合成数据结果解释为生产安全证明；
- 不增加第三个业务场景；
- 不建设复杂场景配置平台。

## 阶段依赖和停止条件

| 阶段 | 可独立演示的结果 | 进入下一阶段的条件 |
| --- | --- | --- |
| 一 | 手动创建通用记忆，并验证场景契约和用户隔离 | 数据模型、依赖守卫和跨用户负向测试通过 |
| 二 | 中性会话自动形成保存、待确认、丢弃和拦截决策 | 原子抽取、准入、敏感和幂等测试通过 |
| 三 | 通用示例完成替代、历史、召回、管理和删除 | 不依赖正式业务插件的 Core 端到端测试通过 |
| 四 | 星海医疗三轮投研闭环 | 投资插件验收和双用户隔离通过 |
| 五 | 第二场景扩展、基线、指标和失败案例完整 | 达到导师确认后的质量门槛 |

如果某阶段失败，不继续堆后续功能，先通过失败案例修正当前阶段。

阶段三是“通用功能完成”的里程碑；阶段四和五是“场景实现与扩展性证明”的里程碑。

## 最终数据模型

| 记录 | 作用 | 首次引入阶段 |
| --- | --- | --- |
| MemoryItem | 逻辑记忆身份、用户、场景和对象 | 一 |
| MemoryRevision | 不可变内容、状态、业务进展和时间 | 一，三完善 |
| Evidence | 来源 turn 和允许保存的片段 | 一 |
| Candidate | 模型抽取结果和准入决策 | 二 |
| ReviewItem | 待用户确认的候选或冲突 | 二，三完善 |
| Relation | 重复、补充、修正、替代和冲突 | 三 |
| Embedding | 语义召回表示 | 三 |
| Usage | supplied 和实际引用记录 | 三 |
| AuditEvent | 关键动作，不保存禁止正文 | 二，三完善 |
| SuppressionMarker | 防止删除内容被旧来源自动重建 | 三 |

设计约束：

- `MemoryRevision` 不原地覆盖；
- 所有用户数据必须有 owner；
- 一条逻辑记忆最多只有一个当前 revision；
- 模型输出不能决定 owner；
- superseded、expired、revoked 不进入正常召回；
- deleted 内容不可恢复；
- `business_progress` 不能代替核心有效状态；
- 正式场景只实现 Core 定义的契约，不能反向修改安全规则。

## 核心接口

实现可以是 Python 方法、HTTP 或其他形式，但业务语义保持稳定：

```text
register_scenario(policy)
capture_turn(principal, turn) -> CaptureResult
query_memory(principal, query) -> MemoryContext
list_memories(principal, filters) -> MemoryList
confirm_memory(principal, review_id) -> MemoryRevision
reject_memory(principal, review_id) -> CommandResult
correct_memory(principal, memory_id, content) -> MemoryRevision
revoke_memory(principal, memory_id) -> CommandResult
delete_memory(principal, memory_id) -> CommandResult
report_usage(principal, answer_turn_id, supplied_ids, cited_ids)
```

阶段一实现注册和最小查询子集，阶段二补齐捕获与确认，阶段三补齐其余通用接口。阶段四、五只注册新的 policy。

## 关键技术取舍

### 1. 模块化单体优先

Memory Core 与 Agent 可以运行在同一个应用中，但通过明确接口隔离。当前没有独立扩缩容和大规模吞吐需求，拆微服务只会增加网络、部署和一致性成本。

### 2. SQLite 是当前原型的权威存储

版本、来源、关系、用户控制和事务都由 SQLite 保存。选择原因是公司终端
不允许安装 PostgreSQL，而 Python 标准库可直接使用 `sqlite3`，无需数据库
服务和额外驱动。Repository port 保持数据库无关，未来出现多人并发、独立
服务部署或生产级隔离需求时再迁移 PostgreSQL。

阶段三的向量表示仍保存在同一 SQLite 数据库中；在合成小数据集上由 Python
执行 owner-scoped 精确相似度计算，不安装 `sqlite-vec` 等本地扩展，也不把
Chroma 作为权威记忆存储。

### 3. 最小场景契约先行，业务接口延后冻结

阶段一先定义 `ScenarioPolicy`，防止 Core 写死投资逻辑；阶段四和阶段五经过两个真实场景后再评估是否冻结接口。暂不建设规则 DSL。

### 4. 同步优先，异步按数据决定

阶段二先同步完成捕获，便于调试和端到端验证。阶段五测量实际延迟后，只有确实影响体验时才引入后台任务和一致性 token。

### 5. 结构化过滤先于语义检索

任何召回都先限定当前用户、已注册场景和有效状态，再做对象、类型和向量相关性。语义检索不能接触其他用户的候选集合。

### 6. 模型理解语义，程序执行规则

模型可以建议类型、关系和用户可能表达的含义。程序必须决定 owner、是否允许保存、状态如何转换、事务如何提交以及用户是否有权查看和管理。

### 7. 场景插件只描述业务差异

场景可以定义类型、业务进展、允许关系、冲突判断和召回优先级，但不能改变用户隔离、来源、版本、敏感、删除和人工控制等核心规则。

## Risks / Trade-offs

- **[通用抽象脱离真实场景]** → 阶段一至三使用中性实例，阶段四、五使用两个差异明显的正式场景校验。
- **[Core 仍然被投资概念污染]** → 增加依赖方向和领域词常量检查，Core 测试只使用 `TestScenarioPolicy`。
- **[ScenarioPolicy 过早冻结]** → 阶段一只确定最小职责，经过两个正式场景后再冻结稳定接口。
- **[五个阶段超出 20 天]** → 优先保证阶段一至三；阶段四保留最小投资闭环；阶段五不实现没有评测证据的优化。
- **[同步捕获增加延迟]** → 阶段二记录实际时延，阶段五再决定是否异步。
- **[模型错误写入长期污染]** → 准入准确率优先、弱推断待确认、来源可见、用户可撤销。
- **[跨用户泄漏]** → 应用层可信身份、Repository SQL 强制 owner 条件、复合
  外键和跨用户负向测试共同防护；明确 SQLite 不等同于生产级数据库授权。
- **[SQLite 并发写入有限]** → 当前原型按单进程、低并发使用，事务保持短小；
  出现多进程写入或独立部署需求时通过 Repository port 迁移 PostgreSQL。
- **[只用向量检索遗漏精确名称]** → 先结合结构化对象过滤，再根据阶段五失败案例决定是否加入全文融合。
- **[删除和来源追溯冲突]** → 区分撤销与删除；删除清除正文，抑制标记不得恢复内容。
- **[用户观点被当成事实]** → 所有阶段保留 assertion kind，回答明确归属用户。

## Migration Plan

这是绿地目标设计，不迁移现有原型状态，也不承诺兼容现有代码。

后续实施严格按阶段进行：

```text
/opsx:apply 阶段一任务
    → 验收通用契约和存储
    → /opsx:apply 阶段二任务
    → 验收通用捕获
    → /opsx:apply 阶段三任务
    → 冻结通用核心里程碑
    → /opsx:apply 阶段四、五场景任务
```

每个阶段完成后：

1. 运行该阶段自动化测试；
2. 使用该阶段对应示例演示；
3. 记录实际偏差和新决策；
4. 必要时先运行 `/opsx:update` 修订后续阶段；
5. 通过退出标准后才进入下一阶段。

任一阶段出现重大方向问题时，可以停止后续任务，而不会留下必须整体推翻的半成品架构。
